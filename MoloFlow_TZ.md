# MoloFlow — Техническое задание

---

## 1. Цель проекта

Веб-сервис для автоматизации списания запасных частей и материалов на предприятии. Инженер получает от склада требования-накладные (Excel), сервис их парсит, распределяет позиции по оборудованию (автоматически или через шаблоны) и формирует сводную таблицу списаний для последующей передачи отчётности в бухгалтерию.

Проект — реальная рабочая задача (не учебная), важен для портфолио, есть желание довести до рабочего состояния до увольнения с текущего места.

## 2. Пользователи

- **Инженер(ы)** — единственные пользователи сервиса. Загружают накладные, распределяют списания, вручную правят закрываемый месяц, управляют открытием/закрытием месяца.
- **Бухгалтер сервисом не пользуется** — ни доступа, ни компетенций для этого у бухгалтерии нет и не предполагается. Бухгалтер получает готовый отчёт по email (см. раздел 3).
- Роль **админа** предполагается (для справочников — компании, оборудование, запчасти) — вероятно, в реальности это тот же инженер с расширенными правами, а не отдельный человек.

## 3. Бизнес-контекст (как это устроено в жизни)

- На предприятии несколько дочерних компаний (на момент обсуждения — минимум две: условно «Идеал» и «Молодец»). Оборудование и запчасти числятся на балансе конкретной компании.
- **Жёсткое правило:** запчасть, числящаяся за компанией А, может списываться только на оборудование компании А. Компания определяется по накладной (в накладной указано, к какой организации она относится) и наследуется на связанные записи.
- Поставщики / контрагенты закупки — **вне системы**. Это не ERP, не нужно связывать запчасть с тем, у кого она куплена. Единственный источник данных — накладная со склада.
- Инженер получает от склада 1–3 накладные в неделю в течение месяца (умеренный объём — до ~15–20 накладных в месяц).
- В конце месяца приходит финальная накладная.
- **Реальная цепочка передачи данных:** кладовщик присылает накладную инженеру на почту (Outlook) → автоматическое вытягивание файлов из писем не рассматривается (нет административных прав на почту/Windows, чтобы это организовать) → инженер **вручную** скачивает файл и загружает его на сайт. В конце месяца инженер на сервисе формирует отчёт и сам отправляет его бухгалтеру по почте (бухгалтер в сервис не заходит).
- После анализа бухгалтером итоговой выгрузки возможны расхождения (ошибки склада, инвентаризация и т.п.) — бухгалтер приносит инженеру бумажную табличку, инженер вручную вносит правки. **Финальный этап ручной правки автоматизировать не нужно.**
- Инженер вручную даёт команду «закрыть месяц» — обычно в один из последних рабочих дней месяца, без жёсткой привязки к календарной дате. Открытие закрытого месяца — предусмотрено, но это аварийный механизм, а не штатный процесс.
- **Важный нюанс дат:** дата, указанная в самой накладной (и в её названии), может относиться к прошлому календарному месяцу, хотя фактически ведётся уже следующий отчётный период. Это нормальная ситуация — отчётные периоды не переключаются по календарю (см. раздел 7).

## 4. Основной результат и смена концепции

**Концепция изменилась по ходу обсуждения:** изначально главная страница = сводная таблица списаний. Теперь решено, что **главная страница отчётом не является** — вместо этого верхнее меню с разделами, а сводная таблица переезжает в один из пунктов меню («Отчёты»). Что именно на главной — пока не решено.

Проект расширяется из «сервиса списания» в подобие внутренней **ERP-системы** для инженерной службы. На данный момент вырисовываются пункты меню:
- **Оборудование** — справочник производств и их оборудования, статус каждой единицы (в работе / консервация и др.), прочая информация, документация.
- **Материалы** — запчасти, остатки на складе, арифметика расхода, минимальные лимиты.
- **Отчёты** — сводная таблица списаний, генерация и выгрузка отчётов (бывшая «главная страница»).
- **ППР** (планово-предупредительные ремонты) — см. раздел 15.
- Возможны другие разделы — список не финальный, будет дополняться.

Функциональность, которая обсуждалась в рамках этого расширения (см. подробнее раздел 14 «Расширение концепции»):
- учёт остатков запасных частей на складе (арифметика: пришло минус списано);
- минимальный лимит на позицию → уведомление в Telegram о необходимости дозаказа;
- статус оборудования (в работе / консервация и т.д.);
- списание с баланса;
- хранение документации по оборудованию и компаниям.

Возможность выгрузки отчётов в Excel с фильтрами (по отчётному периоду, по производству/компании, по оборудованию и т.д.) — сохраняется как ключевая функция, см. раздел 11.

## 5. Ключевой рабочий процесс (workflow)

1. Инженер загружает Excel-файл накладной.
2. Файл валидируется (тип, размер, при необходимости — защита от подмены расширения).
3. Парсер извлекает строки: наименование, количество, единица измерения, номер накладной, компания.
4. Распределение по каждой позиции происходит одним из двух способов:
   - **по готовому шаблону**, ранее сохранённому пользователем или админом (если для запчасти есть ровно один подходящий шаблон — списание автоматическое);
   - **вручную**, если шаблона нет (или их несколько) — пользователю показывается форма выбора оборудования (в рамках компании накладной), с возможностью сохранить выбранный вариант как шаблон на будущее.
5. Каждая строка списания содержит поле «обоснование» — тоже сохраняется в шаблон вместе с распределением, и его можно редактировать перед отправкой, даже если оно взято из шаблона.
6. После обработки — обновление сводной таблицы + уведомление об успехе/ошибке.
7. Если накладная с тем же номером загружается повторно (например, дополнили или исправили позиции) — она **не создаёт вторую накладную**, а создаёт новую **версию** существующей накладной, которая становится активной. Планируется показывать пользователю разницу между версиями (по аналогии с diff на GitHub: что добавилось / что удалилось) — **пока не реализовано, только идея**.
8. Загрузка накладной с датой, попадающей в уже закрытый месяц, — запрещена. Значения прошлых периодов сервису не нужны — сервис стартует с текущего месяца, создание сущностей «в прошлом» запрещено.

## 6. Группировка списаний (важный нюанс, две ситуации)

- **База данных всегда хранит только атомарные факты**: что, сколько, куда, когда — один факт = одна единица оборудования. Никаких агрегированных строк на уровне хранения.
- **Отчёт (Excel для бухгалтерии) — отдельный слой представления.** Там допускается объединять строки по одинаковому названию запчасти и одинаковой дате, если оборудование однотипное (например: «Литол, 12,8 кг, станки 1–10» — одна строка), чтобы бухгалтеру было удобнее читать. Если оборудование разнотипное (станок и упаковочная машина) — обязательно разные строки.
- Правило группировки в отчёте: объединять можно **только** если совпадают `fact_date`, `spare_part`, `equipment`-тип (однотипное оборудование) — никаких «примерно похожих» объединений.
- Хотелка (не решено окончательно): возможность «провалиться» из групповой строки отчёта в разбивку по каждой единице оборудования — вопрос интерфейса, требует проработки.

## 7. Модель «Месяц» (Report Month) — жизненный цикл

Месяц — не календарная сущность, а управляемый объект процесса согласования с бухгалтерией. Всегда существует **ровно один активный** отчётный период; следующий открывается сразу после закрытия предыдущего (можно списывать в него ещё до календарного начала месяца). Два месяца одновременно активными быть не могут.

Состояния (уточнено):
1. **Активный** — идёт обычное списание, ошибки и правки допустимы.
2. **На редакции** — это состояние, в которое попадает **как закрывающийся, так и повторно открытый** (после ошибочного закрытия) период. Новые накладные с этим периодом больше не принимаются автоматически; формируется Excel для бухгалтера; вносятся ручные правки инженера по итогам сверки. Важно: реоткрытие закрытого месяца не возвращает ему статус «активный» — он переходит именно в «на редакции», а не становится параллельным активному.
3. **Закрыт** — данные зафиксированы, факты списания «заморожены», редактирование запрещено (кроме аварийного повторного открытия, которое переводит месяц в статус «на редакции», см. выше).

**Важный инвариант:** факт списания привязывается напрямую к месяцу, а не вычисляется по дате — дата накладной, дата факта списания и отчётный месяц могут не совпадать (это нормальная, регулярная ситуация, а не исключение).

### Отчётный период ≠ календарный месяц (принципиально важно)

Отчётный период («январь» в бизнес-смысле) может не совпадать по датам с календарным январём. Пример: декабрь закрыт за несколько дней до Нового года — но если в оставшиеся дни декабря (например, прямо в новогодние праздники) что-то сломалось и инженер продолжает работать, эти дни фактически уходят в отчётный период «январь» следующего года, хотя календарно это ещё декабрь.

Отсюда — **два разных способа формирования отчёта в интерфейсе**, оба дают отчёт «за январь», но это разные отчёты:
1. **По отчётному периоду** — база помнит фактические границы периода (например, «с 30.12.2025 по 28.01.2026» — это и есть «январь» в системе).
2. **По календарному месяцу** — строго с 1 по 31 января.

### Уникальность и «год» не по календарю

Уникальность отчётных периодов (номер месяца/года и т.п.) привязывается к тому же «плавающему» году, что и сам период — то есть если несколько дней декабря фактически попали в отчётный период следующего года, они учитываются как часть нового года, а не старого. Требует отдельной проработки на уровне модели (как избежать коллизий нумерации).

## 8. Сущности и их назначение

### Company (компания/юрлицо)
Владеет оборудованием и запчастями (баланс). Обязательные связи: Invoice → Company (компания определяется по накладной), через неё проверяется соответствие Equipment/SparePart при списании.
Поля-кандидаты: название (полное/сокращённое), реквизиты (ИНН, КПП, ОГРН, адрес, контакты) — под вопросом, насколько это нужно прямо сейчас; `is_active`.
Отдельно обсуждалась модель `CompanyDocument` (уставные документы и т.п.) — **опционально, не приоритет**.

### Equipment (оборудование)
- Деление на типы — не нужно.
- Может существовать в нескольких экземплярах → нужен порядковый номер + уникальный инвентарный номер.
- Принадлежит Company.

### SparePart (запасная часть / материал)
- Название хранится **как есть**, без нормализации (lower/strip и т.п.) — намеренное решение, потому что в реальности разные написания могут быть разными позициями, и парсер должен быть честным источником, а не «догадываться».
- Принадлежит Company.
- Единица измерения — **не свойство SparePart**, а свойство конкретной строки (см. ниже) — одна и та же запчасть может приходить в разных единицах (штуки/упаковки/кг).

### Unit (единица измерения)
- `name`, `symbol`, `aliases` (список альтернативных написаний, распознаваемых парсером) — реализовано как `JSONField(default=list)`.
- Позволяет добавлять новые варианты написания без изменения кода.

### Invoice (накладная)
- `number` — номер накладной. **Открытый вопрос:** изначально стоял `unique=True`, но решено отказаться от глобальной уникальности номера, так как нумерация со временем может обнуляться (например, по годам), а дата будет другой — нужна отдельная логика формирования/проверки номера, пока не доделана.
- `date` — дата накладной.
- `active_version` — FK на текущую активную версию.
- Компания определяется через содержимое накладной (парсер видит название организации в файле).

### InvoiceVersion (версия накладной)
- Полноценное версионирование по типу git-истории: каждая повторная загрузка накладной с тем же номером создаёт новую версию, не удаляя предыдущую.
- `unique_together(invoice, version)`.
- Хранение файлов: без отдельных папок на версию — просто добавление номера версии к имени файла (`invoice-<номер>-v<версия>`), решено как достаточное при текущем объёме (2–4 накладных в неделю, до ~16/мес, ~208/год).
- Обсуждался (но отклонён на данном этапе) вариант с добавлением уникального суффикса (id/timestamp) к имени файла — решили, что это ухудшит читаемость без реальной пользы при текущих объёмах.

### InvoiceItem (строка накладной)
- Поля: `name` (как в накладной), `quantity` (Decimal, `max_digits=10, decimal_places=2`, с валидатором `MinValueValidator(0.01)`), `unit` (FK на Unit, может быть `null` если не распознано), `version` (FK на InvoiceVersion).
- **Пересмотрено:** изначально решили не хранить стоимость — теперь, в связи с задачей учёта остатков на складе (см. раздел 14), это меняется. Нужно дополнительно парсить и хранить:
  - **затребовано** и **отпущено** (в накладной это отдельные графы) — если цифры не бьются между собой, интерфейс должен показывать алерт-предупреждение («обрати внимание»), а не блокировать загрузку;
  - **цена** и **сумма** по позиции — нужны, поскольку появляется задача остатков по складу, и через них удобнее искать/сверять наименования в базе.
- **Сложность парсинга (важно для реализации):** реальные Excel-файлы от склада могут быть неаккуратно оформлены — названия в кавычках, возможны две «шапки» таблицы и другие форматные сюрпризы. Парсер должен быть устойчив к этому, а не рассчитан на идеально чистую таблицу.

### Template (шаблон распределения)
- Связывает SparePart + Equipment + обоснование, с флагом авто/ручного распределения.
- Если для запчасти шаблон единственный — списание автоматическое; если несколько — форма выбора.

### WriteOffFact (факт списания) — ключевая сущность, спроектирована последней и наиболее тщательно
Это **событие**, а не свойство SparePart — списание не «прилипает» к запчасти, а фиксируется отдельным атомарным фактом: что, сколько, куда, когда.

Поля (зафиксированные по итогам обсуждения):
- `spare_part` (FK)
- `equipment` (FK)
- `fact_date` — обязателен, **не выводится** из даты накладной (дата накладной ≠ дата фактического списания ≠ отчётный месяц — это регулярная, а не редкая ситуация)
- `report_month` — факт принадлежит месяцу напрямую (не вычисляется по дате)
- `quantity` — Decimal (тот же тип, что в InvoiceItem, для единообразия)
- `unit` — FK на Unit, может отличаться от `InvoiceItem.unit` (пример: пришла «1 коробка», списали «24 штуки» — конвертация единиц отложена на будущее, не в MVP)
- `company` — обсуждался вопрос «а зачем поле company, если её можно получить через equipment/spare_part» — решили: не обязательна как источник данных, но полезна как инвариант (защита от рассинхрона) и оптимизация запросов.
- `source` — `invoice` или `manual`. Immutable для конкретного факта (не меняется при коррекции).
- `status` — `active` / `cancelled`. Факт **immutable** по ключевым полям (spare_part, equipment, fact_date, quantity); любая коррекция = отмена старого факта (`cancelled`, история сохраняется) + создание нового с нужным `source` (`manual`, если правил инженер).
- Snapshot принадлежности: если оборудование/компания позже станут неактивными или сменят принадлежность — на уже созданные факты это **не влияет** (используется snapshot на момент создания факта, а не текущее состояние).
- Обязательная валидация при сохранении: `equipment.company == spare_part.company`, иначе ошибка.

**Правило группировки для отчёта** (см. раздел 6) применяется к WriteOffFact при формировании Excel, но не к хранению.

Ещё не решено окончательно: два дополнительных поля для полноты факта — упомянуты как «то, что осталось обсудить», но в тексте не зафиксированы конкретно (только источник и статус уже разобраны).

## 9. Структура Django-приложений (согласованная архитектура)

- **core / equipment** — статичные справочники: `Company`, `Equipment`, `SparePart`, `Unit`. Ничего не знает про месяцы, факты, накладные. Односторонняя связь: `invoices` ссылается на `equipment`, обратной связи нет.
- **invoices** — домен процесса и фактов: `Invoice`, `InvoiceVersion`, `InvoiceItem`, `Month` (ReportMonth), `WriteOffFact`, `Template`, `Justification`.
- **users/accounts** (опционально) — кастомный пользователь, роли.
- **reports** (опционально, позже) — агрегация и выгрузка Excel/CSV, графики. Не хранит собственных моделей, читает WriteOffFact.
- **notifications/common** (опционально, позже) — логи, уведомления.

## 10. Валидация загружаемых файлов

- Разрешённый формат — только Excel (.xlsx/.xls).
- Проверка по расширению **и** MIME-типу (расширение можно подделать, поэтому нужна комбинация).
- Обсуждалась идея единого `InvoiceFileValidator`, закрывающего разом: тип файла, MIME, дубликаты, размер файла — **не доведено до конца, требует изучения (BytesIO, openpyxl/xlrd, python-magic)**.
- Резервирование при ошибке записи: не бэкап всей БД на каждую операцию, а `transaction.atomic()` + откат + сохранение исходного файла и лога ошибки. Пока факт не подтверждён — статус `draft`, после подтверждения — `committed`.

## 11. Отчётность

- Сводная таблица (теперь на отдельной странице «Отчёты», не на главной) — все списания, серверная пагинация по количеству строк (индексы по date, production/company, equipment, sparepart).
- Формирование отчёта — по двум разным основаниям периода: по отчётному периоду или по календарному месяцу (см. раздел 7) — это разные отчёты, оба должны быть доступны.
- **Два варианта формирования выгружаемого отчёта:**
  1. Единый лист со всеми списаниями по всем производственным линиям.
  2. Разбивка по производственным линиям (например, вафельное производство, производство печенья и т.д.), внутри — хронологически.
- В интерфейсе сервиса (не только в выгрузке) — возможность раскрыть сгруппированную строку отчёта и увидеть дробное списание по каждой единице оборудования (см. также раздел 6).
- При просмотре активного (незакрытого) отчётного периода в интерфейсе — подсвечивать последние добавленные строки списаний.
- Экспорт: Excel/CSV (через pandas), с фильтрами (период, компания/производство, оборудование).
- Графики/диаграммы — нужны, но конкретика (какие именно, какая библиотека) **не проработана**.

## 12. Расширение концепции — учёт остатков и лимиты

Отдельный крупный блок, добавленный в проект по ходу пересмотра:

- **Остатки запасных частей на складе.** Инженер ежемесячно запрашивает фактические остатки — их нужно можно будет вносить в сервис. Дальше — арифметика: остаток = (сколько пришло по накладным) − (сколько списано), с учётом ручных корректировок остатка.
- **Минимальный лимит на позицию.** Для каждой запчасти/материала можно задать минимальный порог. При достижении/превышении порога вниз — уведомление в **Telegram** (бот) о необходимости дозаказа. Всплывающие уведомления внутри интерфейса сервиса — сознательно **не делаем**, только Telegram.
- **Справочник производств и оборудования** — по факту дублирует/расширяет уже описанные Company/Equipment, но с более полным набором атрибутов: статус оборудования (в работе / консервация и т.п.), прочая информация.
- **Списание с баланса** и **хранение документации** (по оборудованию, компаниям) — тоже часть этого расширения, детали не проработаны.

Это превращает MoloFlow из узкоспециализированного сервиса списания в подобие внутренней ERP для инженерной службы — соответственно, объём проекта заметно вырос по сравнению с первоначальной идеей.

## 13. Модуль ППР (планово-предупредительные ремонты)

Новый раздел меню и функциональность:

- ППР — регламентный документ, который на предприятии уже существует в виде таблицы: строки — оборудование, столбцы — месяцы (**календарные**, не отчётные периоды — это принципиально), на пересечении — если ячейка не пустая, значит в этом месяце по этой единице оборудования запланировано обслуживание/ремонт (содержание ячейки — что именно).
- Сервис должен **хранить сканы** документов ППР (отдельный пункт меню).
- Со сканов нужно **парсить** понимание того, какое оборудование в каком месяце должно обслуживаться (требует OCR/распознавания — конкретный инструмент не выбран, требует изучения).
- На основе этого — **рекомендации**: если по плану в текущем календарном месяце для какой-то единицы оборудования запланировано обслуживание, а по факту по ней ничего не списано — сервис должен вывести рекомендацию/напоминание об этом (пример: «компрессор такой-то — по плану обслуживание есть, но списаний по нему не было»).
- Форма подачи рекомендаций — отдельная табличка на вкладке «ППР» (не всплывающие уведомления — их сознательно решили не делать, ни в интерфейсе, ни всплывающими окнами, только статичная таблица в разделе ППР).
- Важно: логика привязки рекомендаций — **строго к календарному месяцу**, а не к отчётному периоду (в отличие от списаний, которые живут в отчётных периодах).

- БД: SQLite для разработки, PostgreSQL для прода (упоминались JSONB и полнотекстовый поиск как потенциально полезные).

### Несостыковки кода с ТЗ и найденные баги (аудит)

1. **Баг статусов WriteOffFact:** `constants.STATUS_CHOICES` определяет `"cancelled"` (двойное L), а методы модели (`cancel()`) сравнивают/присваивают `"canceled"` (одно L). Из-за этого отмена факта не будет соответствовать choices, а `WriteOffFact` не использует `FullCleanSaveMixin`, поэтому `full_clean()` не вызывается при сохранении — некорректное значение статуса может тихо попасть в базу.
2. **Конфликт по `Unit`:** зафиксировано в ТЗ, что единица измерения — свойство строки накладной (одна и та же запчасть может приходить в разных единицах), но в коде `SparePart.unit` — жёсткий FK, то есть единица привязана к самой запчасти. Нужно осознанно решить: либо убрать `unit` из `SparePart`, либо задокументировать, что решение поменялось и почему.
3. **`WriteOffFact` не хранит `unit`** — а по ТЗ списанная единица измерения может отличаться от единицы в накладной (кейс «коробка» → «24 штуки»). Сейчас в модели этого поля нет.
4. **`ReportMonth` не покрывает новую концепцию** отчётного периода: нет статуса «на редакции» (только открыт/закрыт), нет хранения фактических дат начала/конца периода, нет «плавающего» года. Это самый существенный архитектурный разрыв между кодом и актуальным ТЗ (см. раздел 7).
